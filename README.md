# YOLO26n 装甲板视频推理

基于 [Ultralytics YOLO](https://github.com/ultralytics/ultralytics) 的 **YOLO26n-pose** 装甲板检测与关键点推理脚本，用于 RoboMaster 视觉学习与验证。

输入一段视频，逐帧推理，检出目标时绘制**检测框、类别、置信度，以及模型预测的 4 个关键点**，最后导出可正常播放的结果视频。

---

## 1. 项目完成的功能

| 编号 | 功能 | 对应实现 |
| --- | --- | --- |
| 1 | 加载模型权重，读取视频 | `YOLO(weights)` + `cv2.VideoCapture(VideoCapture)` 逐帧读取 |
| 2 | 对视频执行推理 | 每帧送入 `model.predict()` |
| 3 | 检出目标时绘制检测框、类别、置信度、**4 个关键点** | 见下文"绘制内容说明" |
| 4 | 保存内容对应、能正常播放的结果视频 | `cv2.VideoWriter`，编码器自动降级选择 |

**关于关键点的说明（重要）**

关键点取自模型 **pose 分支的真实预测输出** `results.keypoints.xy`，形状为 `[N, 4, 2]`：

- `N` = 该帧检出的目标数
- `4` = 每个目标 4 个关键点
- `2` = 每个关键点的 (x, y) 坐标

**没有使用检测框的四个角代替关键点。** 本次运行的统计可以直接验证这一点：

```
检出目标:   715 个
有效关键点: 2860 个
715 × 4 = 2860   ← 每个检出目标都输出了完整的 4 个真实预测点
```

**绘制内容说明**

检出目标后，在同一帧上绘制三部分：

1. **检测框** —— 颜色按类别 id 稳定生成（同一类别颜色固定）
2. **类别 + 置信度** —— 例如 `R1 0.87`，带同色底色块，任何背景下都清晰
3. **4 个关键点** —— 每个点三层绘制（白色外圈 + 彩色内点 + 黑色描边），点旁标注序号 `0 1 2 3`；加 `--link-kpts` 会按顺序连线成四边形，便于分辨点的归属

无效点处理：坐标为 `(0, 0)` 或明显偏离对应检测框的点，判定为无效预测并跳过绘制。

## 3. 模型权重的准备方式与放置位置

### 权重来源

`best.pt` 由课程参考材料提供，**本次作业不重新训练模型，直接使用该权重做推理**。

### 权重类型（从模型文件元数据读出）

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `task` | `pose` | 姿态估计模型（非普通检测） |
| `kpt_shape` | `[4, 2]` | 每目标 4 个关键点，各含 (x, y) |
| `nc` | `6` | 6 个类别 |
| `names` | `B1 B2 B3 R1 R2 R3` | 蓝方 / 红方各 3 类装甲板 |

训练来源路径显示基础模型为 `yolo26n-pose.pt`，数据集为 RMUL 装甲板关键点数据集，该权重由 yolo26x-pose 蒸馏到 yolo26n 得到（体积仅 5.62 MB）。详细分析见 [`docs/model_info.md`](docs/model_info.md)。

### 放置位置

权重文件**不提交到 Git**（已在 `.gitignore` 中通过 `*.pt` 排除），运行前需自行准备。脚本默认从以下位置读取：

```
D:\桌面\best.pt
```

若权重放在别处，用 `--weights` 参数指定即可，无需修改代码：

```bash
python infer.py --weights D:\weights\best.pt --video D:\videos\rm.mp4
```

也可以直接修改 `infer.py` 顶部的 `DEFAULT_WEIGHTS` 常量。

## 4. 安装步骤与运行命令

### 4.1 安装依赖

```bash
# 进入项目目录
cd /d D:\yolo-armor-inference

# 创建虚拟环境
python -m venv .venv

# 激活虚拟环境（Windows）
.venv\Scripts\activate

# 安装依赖（国内建议加清华源）
pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

激活成功后命令行提示符前会出现 `(.venv)` 标记。

> 若 `pip install` 未使用镜像源，torch 下载可能非常慢。建议保留 `-i` 参数。

### 4.2 实际运行命令

```bash
python infer.py --video "D:\桌面\RM视频.mp4"
```

带可选参数的完整示例：

```bash
# 放大关键点并连线，便于观察关键点归属
python infer.py --video "D:\桌面\RM视频.mp4" --kpt-radius 8 --link-kpts

# 指定权重、置信度阈值与输出路径
python infer.py --weights D:\桌面\best.pt --video "D:\桌面\RM视频.mp4" --conf 0.4 --out D:\result.mp4

# 强制使用 CPU
python infer.py --video "D:\桌面\RM视频.mp4" --device cpu
```

### 4.3 参数说明

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--weights` | `D:\桌面\best.pt` | 模型权重路径 |
| `--video` | **必填** | 输入视频路径 |
| `--out` | `runs/infer/video_result.mp4` | 输出视频路径 |
| `--conf` | `0.25` | 置信度阈值 |
| `--iou` | `0.45` | NMS IoU 阈值 |
| `--imgsz` | `640` | 推理分辨率 |
| `--device` | 自动 | `cpu` 或 `0`（GPU 序号） |
| `--show` | 关闭 | 实时显示推理画面（按 `q` 退出） |
| `--kpt-radius` | `5` | 关键点圆点半径（像素） |
| `--link-kpts` | 关闭 | 用连线串起 4 个关键点 |
| `--link-order` | `0-1-2-3-0` | 连线顺序，`none` 表示不连 |
| `--box-thickness` | 自动 | 检测框线宽，默认按分辨率计算 |
| `--no-labels` | 关闭 | 不绘制类别与置信度标签 |

**模型路径、视频路径、输出位置三者均可通过命令行参数修改，无需改动代码。**

### 4.4 结果保存位置

```
D:\yolo-armor-inference\runs\infer\video_result.mp4
```

- 输出视频**保持原视频的分辨率与帧率**，画面内容与源视频逐帧对应

## 7. 实际识别表现与问题记录

### 7.1 整体统计

本次推理在 486 帧视频上的实际输出：

| 指标 | 数值 |
| --- | --- |
| 处理帧数 | 486 |
| 含检出的帧数 | **484 / 486（99.6%）** |
| 检出目标总数 | 715 |
| 有效关键点总数 | 2860（= 715 × 4） |
| 平均每帧检出 | 约 1.5 个目标 |
| 输出视频大小 | 11.73 MB |

### 7.2 识别表现

- **召回情况良好**：486 帧中有 484 帧检出了目标，仅有 2 帧无任何检出，基本实现了全程连续跟踪
- **关键点完整**：715 个检出目标共输出 2860 个关键点，恰好等于 `715 × 4`，说明每个目标都输出了完整的 4 个点，未出现漏点
- **类别区分正常**：结果显示模型能区分 `B*`（蓝方）与 `R*`（红方）以及不同编号的装甲板
- **无跨阵营误检**：本视频画面中**只有蓝色方装甲板**，实际检测结果也**只出现 `B1`/`B2`/`B3` 类别，没有把蓝方装甲板误判为红方 `R*`**。这说明模型对红蓝双方的特征区分是有效的，而不是靠位置或外观猜测——在只有单一阵营的场景下没有凭空产生另一阵营的误检，可以排除一类典型的误检情形

### 7.3 遇到的问题与处理方法

**问题 1：模型输出的是 `[4, 2]` 而非 `[4, 3]`，无法按关键点置信度过滤**

- **现象**：一般姿态模型（如人体关键点）输出 `[K, 3]`，第三个值是可见性置信度；本模型 `kpt_shape = [4, 2]`，只有坐标没有置信度
- **处理**：改用坐标合理性判断——坐标为 `(0, 0)`，或明显偏离对应检测框（超出框宽/框高 35%）的点，判定为无效预测并跳过绘制，避免画出飞到画面外的点

**问题 2：中文路径导致控制台输出报错**

- **现象**：输入视频路径含中文（`D:\桌面\RM视频.mp4`）时，Windows 控制台默认 GBK 编码，`print()` 中文路径会抛 `UnicodeEncodeError` 并中断整个推理
- **处理**：在脚本开头把标准输出重定向为 UTF-8：

  ```python
  sys.stdout.reconfigure(encoding="utf-8", errors="replace")
  ```

**问题 3：视频编码兼容性**

- **现象**：`cv2.VideoWriter` 使用固定编码器时，在部分环境下会创建失败或生成无法播放的文件
- **处理**：实现编码器自动降级（`mp4v` → `avc1` → `XVID` → `MJPG`），并自动调整输出扩展名，确保一定能生成可播放的结果视频

**问题 4：Python 3.13 的兼容性**

- **现象**：部分教程建议 Python 3.8~3.11，担心新版无预编译包
- **处理**：先确认 `torch`（2.6.0 起支持 3.13）与 `ultralytics` 均有适配 wheel，实测在 3.13.15 上安装与运行正常，无需降级 Python

### 7.4 漏检与误检的真实记录

按要求逐帧查看结果视频后，实际观察到的现象如下，**未对结果做美化处理**。

#### 现象一：遮挡 + 弱光导致的漏检（确认存在）

机器人运动过程中出现侧倾姿态时，**存在漏检**。典型帧见结果截图（约第 3 秒）：

- **本帧只有 1 个目标被检出**，标注为 `B3 0.68`
- 画面右侧**另有一块蓝方装甲板未被检出**
- 该帧的检出置信度仅 `0.68`，明显低于正常光照下的水平

**成因分析：**

1. **遮挡** —— 机器人侧倾时，装甲板被车体结构部分遮挡，可见区域不完整
2. **光照不足** —— 未检出的那块装甲板朝向镜头的是内侧与底部，处于阴影中，蓝色灯条与周围的对比度显著下降

两者叠加使得该目标置信度落到阈值 `0.25` 之下。同一帧中唯一检出的目标置信度也只有 `0.68`，说明**这段画面整体的成像条件偏难**，并非模型在正常条件下的表现。

#### 现象二：关键点位置准确（未发现明显偏差）

在检出成功的帧中，**4 个关键点连成的四边形与装甲板轮廓基本吻合**，机器人转动时关键点随之转动，未观察到偏离装甲板的现象。这说明 `[4, 2]` 模型虽然不输出关键点置信度，但坐标预测质量是可靠的。

#### 现象三：未发现跨阵营误检

画面中**只有蓝色方装甲板**，检测结果中也**只出现 `B1` / `B2` / `B3` 类别，没有出现任何红色方 `R*` 的误检**。可以排除"把蓝方误判为红方"这类类别错误。

#### 现象四：未发现对非装甲板物体的误检

地板、机器人车体结构、线缆等物体**均未被误框为目标**，未观察到明显误检。

> 说明：本项结论基于对结果视频的抽样查看，如后续逐帧复核发现例外情况，将补充记录。

#### 结论

本视频的主要问题是**遮挡与弱光条件下的漏检**，而非误检或类别错误。在光照充足、装甲板完整可见的帧中，检测与关键点预测均正常。若需改善该类场景的表现，可考虑：降低 `--conf` 阈值（代价是可能引入误检）、提高 `--imgsz`、或在训练数据中补充遮挡与弱光样本。

### 7.5 若出现全片无有效检出的排查思路

本次运行有检出，未触发该情况。若换用其他视频时出现全片零检出，按以下顺序排查：

1. **确认权重** —— 检查 `--weights` 指向的文件是否存在且为 pose 模型；脚本启动时会打印 `任务类型` 与 `关键点形状`，若显示 `task='detect'` 说明权重传错
2. **确认视频输入** —— 检查路径是否正确、视频能否被 `cv2.VideoCapture` 打开；脚本第 2 步会打印分辨率与帧率，若为 `0x0` 说明读取失败
3. **调整推理参数** —— 降低 `--conf`（如 `0.1`）排除阈值过高的影响；提高 `--imgsz` 改善小目标；确认 `--device` 设置合理
4. **确认内容匹配** —— 检查视频中是否确实存在模型认识的装甲板。用无关内容（如风景、录屏）测试必然为零检出，这属于正常现象而非故障
